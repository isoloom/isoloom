- **Library: the targets made of two backends are composed in `isoloom-targets`,** so no backend depends on another: `isoloom_targets::composite::{CloudDockerBackend, DockerVmBackend, HybridBackend}` (also re-exported by `isoloom_targets::backends`) replace `isoloom_terraform::cloud_docker::CloudDockerBackend` and `isoloom_vagrant::{DockerVmBackend, HybridBackend}`. The container helpers the backends share (`CHECK_IMAGE`, `PROBE_IMAGE`, `PROBE_DIR`, `UTILITY_IMAGE`, `probe`, `ready_test`, `exec_runner`, `leaf_jobs`, `start_commands`, the project-file variables and `host_environment`) live in `isoloom_render::container` (still re-exported by `isoloom_compose`), and the hybrid containers' Compose file is `isoloom_compose::hybrid::render`. Generated files are unchanged.

A new core crate has to be placed in the core order (spec and manifest, catalogue, plan, render), and a crate outside `crates/{core,backends,tools,targets,cli}/` fails.
- **The ratchet, `cargo xtask quality [--update] [--table]`:** counts, per crate, every clippy and rustc warning (`clippy/<lint>`, `rustc/<lint>`), source files over 400 lines of code (`file/over-400-loc`, which replaces `crates/core/isoloom-spec/tests/code_size.rs`), duplicated blocks (`dup/clone`, jscpd 5.4.1 through `npx`, so it needs Node), unused and machete-ignored dependencies (`machete/unused`, `machete/ignored`) and the exceptions (`exception/expect`), against `quality-baseline.json`. A count that goes up fails it; `--update` writes the counts only when none went up; with no baseline, the first measure is written.
- **The lint set is the strictest (PLAN 1c), in the workspace `[lints]` table:** at deny where the count is zero (rustc `unused` and `missing_docs`; clippy `all`, `pedantic`, the size limits, `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented`, `dbg_macro`, `print_stdout`, `wildcard_imports`, `clone_on_ref_ptr`, `rc_buffer`, `get_unwrap`), at warn where it isn't yet (`unreachable_pub`, `allow_attributes`, `allow_attributes_without_reason`, `doc_markdown`, `missing_errors_doc`, `must_use_candidate`, `similar_names`, `print_stderr`, `indexing_slicing`, `string_slice`, `as_conversions`, `shadow_unrelated`, `let_underscore_must_use`, `str_to_string`). `cargo clippy -- -D warnings` therefore no longer passes: the gate is `cargo clippy` (deny-level lints fail it) plus `cargo xtask quality`, and `cargo xtask check-all` runs both. An unused item now fails `cargo build` too. Tests may also index and slice (`allow-indexing-slicing-in-tests` in clippy.toml). An exception is `#[expect(lint, reason = "...")]`.

## Phase 2: the spec front end
- **`checks[].wait` takes a duration** as well as seconds: `90`, `90s`, `3m`, `1m30s` (held in seconds; the run manifest's timeouts read it).
- **A VM with no set-up steps is valid:** a machine that is its OS alone is a machine of its own; validation no longer asks for `vm.provision` steps.
- **A secret no machine gets** is reported with the fix "place it as a file, `files: [{ path, secret: <name> }]`".
- **A container machine's set-up jobs run as root** (`user: root` on each `<machine>-init-<n>` Compose service), with the machine's files, its `privileged` and, on a gateway, `NET_ADMIN`.
- **Library (`isoloom-spec`):** `syntax` is the new format (types, `parse`, coded `Problem`s with spans, `check`, the forms a machine takes); `os::container_image` gives each Linux OS's official image pinned by digest; `model::SecretSource::Input` and `model::Generated` are set by lowering only.
- **Library (`isoloom-plan`):** `lower::lower(&syntax::Spec, Scope)` lowers the new format into the model per target, with refusals at the written field path; `Lab` wraps an authored spec (validation, possible targets, per-target lowering); `Build` is `Own` or `Generated`; `PublishedPort` has a `name`; `SecretFile` has a `source` (`ValueSource::{Secret, Input}`); `Step::Setup` runs a VM's `setup` scripts once its command started.
- **Library (`isoloom-render`):** `dockerfile` renders the Dockerfile generated from a machine's portable steps, at `.isoloom/docker/build/<machine>/Dockerfile`.
- **The spec is in the new format** (`plan/phase2/spec.md`); `docs/spec.md` and `isoloom schema` describe it. A machine has an `os` (`<family>@<version>`, e.g. `debian@12`, `windows-server@2022`, `kali@rolling`), an `app:` (`image`, `build` as a folder or `{ context, dockerfile, target, args }`, or `appliance` with `image`, `config`, `firmware`; plus `steps:` `{ run }`, `{ run, creates }`, `{ copy }`, `{ packages }`, `{ playbook }`, `reboot`), or its OS alone. `hardware:` holds `arch`, `gpus`, `devices`, `nested_virtualization`, `tpm` (`auto`, `required`, `none`) and `boot`; `command:` is a text, a list or `{ run, cwd }`; `setup:` lists scripts; `environment:` values are text or `{ input: NAME }`.
- **Ports are a map keyed by name** (`[a-z][a-z0-9-]*`, unique per machine): `ssh: 22` (TCP), or `{ port, protocol, publish, dormant }` with `protocol` one of `tcp`, `udp`, `http`, `https`, `tls`, and `publish` `true`, a host port, or `{ host, fixed: true }`.
- **`files:`** take exactly one of `content`, `source` (a project file), `secret` or `input`, with `path` absolute and optional `uid`, `gid`, `mode`; a file from a secret or an input defaults to mode `0400` on every target (a container's secret files were `0444`).
- **`overrides.<target>`** holds what only one target reads, as fixed fields: `docker` (`networks.<n>.cidr`, `networks.<n>.external`, `volumes.<v>.external`), `kubernetes` (`volumes.<v>.external`), `proxmox` (`machines.<m>.image`, `machines.<m>.lxc`, `networks.<n>.external`, `volumes.<v>.virtiofs`), `esxi` (`networks.<n>.external`), `vagrant` (`machines.<m>.box`, `box_version`, `boxes.{qemu,hyperv}`, `winrm`, `winssh`, `box_url`, `box_server_url`; `controller.box`, `controller.box_version`), each cloud (`machines.<m>.image`) and `external` (`machines.<m>.ssh`). A `machines` key may name a group.
- **The old keys are refused, never read:** `docker:`, `vm:`, `services:` and a machine's `inputs:`/`secrets:` each give a problem with the fix in the new format; a port list gives "ports are a map of named ports". `service:` is refused: the catalogue arrives in Phase 4.
- **`isoloom validate` problems** carry a code (`unknown-field`, `removed-field`, `missing-field`, `invalid-value`, `conflict`, `unknown-reference`, `sensitive-value`, `refused`), the field path as written, the line and column, the reason and the fix: `✗ error[<code>] <path>  (isoloom.yml:<line>:<column>)`, the reason, then `fix: …`. `--json` keeps `{ ok, problems }`; each problem is `{ code, path, line, column, reason, fix }`.
- **A machine's forms:** the container form is its `app.image`, `app.build` or `app.appliance`; else, with an `os`, a Dockerfile Isoloom generates from the OS's official image (pinned by digest) and the steps `run`, `copy` and `packages`; else the OS's image kept idle. The VM form is its `os` with its steps. A `reboot` or `playbook` step, a `.ps1`, a Windows `os`, or VM-only hardware (`tpm: required`, `nested_virtualization`, `boot`) rules out the container form; host `devices` rule out the VM form; `app.build`/`app.appliance` without `os` have no VM form. A target refused for a missing form names the written field (`machines.web.app.build: a Dockerfile builds a container only`).
- **A machine whose steps install services needs a `command` to have a container form:** `os` + `app.steps` + `ports` without `command` has none (containers have no init, so nothing would answer). The container targets refuse it at `machines.<m>.command` ("its steps install services, but nothing keeps one running in a container"), with the fix "add `command:` (the service in the foreground), or use a catalogue `service:` (Phase 4)"; its VM form is unchanged.
- **`tc` values and `rate_limit` can't be negative:** `-5ms` for `delay` or `jitter`, `-10mbit` for `rate` or `rate_limit`, are refused at validation ("a delay can't be negative"); netem refused them only when the lab ran.
- **The `corp-ad-basics` example runs its domain playbooks from the controller** (`provision:`, over WinRM) instead of as Windows steps, and now generates on `vagrant`, `hybrid`, `proxmox` and `esxi` (it generated on no target before).
- **A `playbook` step on a Windows machine is refused at validation** (`machines.<m>.app.steps[<i>].playbook`, fix "`{ run: <script>.ps1 }`"), instead of by every target when generating.
- **`copy` and `packages` steps build into the container form only, for now:** a VM target refuses the machine at `machines.<m>.app.steps[<i>]` ("comes with the configuration backends (Phase 4)"), with the fix "write it as a `run:` script for now, or use a container target".
- **An access machine with an `os`** is a machine of its own on the container targets too (its OS's image, kept idle), not the runner's `isoloom-access` helper; without an `os` the runner supplies it on every target, as before.
- **`setup:` scripts run on both forms, once:** on containers as the `<machine>-init-<n>` Compose jobs (Kubernetes: init containers), on VMs as one step named `setup` after the machine's command started, skipped when `/var/lib/isoloom/setup.done` exists.
- **Inputs are sensitive by default;** a sensitive input may not be an environment value (`sensitive-value`): it reaches a machine as a file, `files: [{ path, input }]`. Compose gets it as a secret sourced from the environment (`environment: <INPUT>`, kept with its uid, gid and mode; the container's environment holds no value), Kubernetes as a Secret mounted at the path, VMs (Windows included, which never got their inputs before) through the secrets `isoloom run` delivers. An input marked `sensitive: false` may be an environment value.
- **An input in `environment` keeps its own name, for now:** `URL: { input: API_URL }` is refused (`refused`, fix "`API_URL: { input: API_URL }`"); the variable is the input's name.
- **A secret's or an input's value goes to the resume step too:** the docker manifest delivers each slot to `up` and `start` (and the leaf jobs). Compose writes a secret's file again from its variable every time it starts the container, and refuses to start without the variable (Compose 5.5.1), so `resume` needs the value again; `stop`, `down`, `ps` and `exec` don't.
- **A run manifest's secret slot may carry a `default`:** what the runner delivers when it has no value. The docker manifest gives every input slot `default: ""`, so a lab started without an input, and every resume, still creates and starts its containers (the input's file is empty) instead of Compose refusing an unset variable.
- **An input's `sensitive: false` reaches its run manifest slot** (`sensitive: false`, shown in the runner's events and logs); an input the spec says nothing of stays masked.
- **Compose's minimum version** in the run manifest is 2.17.0 (`--wait-timeout`); secrets from the environment need 2.14.1, which it covers.
- **Published ports are named everywhere:** the Compose label is `isoloom.port.<name>`, Terraform's published-port outputs are keyed `<machine>/<name>`, `resolved.json` (version 3) holds each machine's `ports` as a map by name with `published` and, for `http`/`https`, `url`, and its `published` list carries `name` and `protocol`. A message reads `{{ machines.<m>.ports.<name>.published }}`, `.port` or `.url`.
- **Run manifest:** a machine's ports have a required `name`, unique per machine; `${published.<machine>.<port name>}` replaces `${published.<machine>.<number>[.udp]}`, and a `published_port` output names its port (`{ kind, machine, port: <name> }`).
- **`isoloom import`** writes the new format: `app:` (`image`, `build`), named ports (`ssh`, `http`, `postgres`…, else `p<number>`, `-udp` for UDP), `os`, `app.steps` from provisioners, a Compose service's interpolated variables as non-sensitive inputs in `environment`, and a Vagrantfile's boxes under `overrides.vagrant`.
- **Library (`isoloom-spec`):** `Spec` is the authored spec (`syntax::Spec`); `parse` and `load` return it, and refuse an invalid one with `LoadError::Invalid { file, problems }`; `model::from_yaml` reads the lowered form directly (tests only, for now). `isoloom_targets` functions (`generate`, `refusal`, `resolved::*`, `render_message*`) take a `&Lab`.

## Phase 2: the Isothrum runner skeleton (Isothrum repository)
- **Layout:** `crates/isothrum-core` is now `crates/isothrum-compiler` (crate `isothrum-compiler`); `crates/isothrum-wasm` keeps its name, so the WASM npm package is unchanged. New: `crates/isothrum-runner` (the library), `crates/isothrum-cli` (the `isothrum` binary) and `xtask/` (`cargo run -p xtask -- schema | real-run`).
- **Isoloom dependency:** Isothrum depends on `isoloom-spec`, `isoloom-targets` and `isoloom-manifest` by git URL, pinned to a commit of Isoloom's local main; `cargo xtask dev-link link` (in Isoloom) points them at the local checkout. The `isoloom-core` facade is gone from the libraries (the desktop app still pins it).
- **The compiler on Isoloom's current model:** a node's `services` (editor JSON) become the machine's `ports`; OS names are `<family>@<version>`; the WASM plan reads the spec back through Isoloom's parser, as `isoloom generate` reads the download.
- **`isothrum` commands:** `up`, `down`, `park` (`--mode pause|shutdown`, default `shutdown`), `resume`, `status`, `check` and `events`, each on a lab folder (default `.`) whose `.isoloom/<target>/run.json` is read (the only one, or `--target <t>`), or on a `run.json` given directly. Exit 0 done, 1 failed (a failing check included), 2 a usage error.
- **`isothrum` options:** `--name` (the run's name, default the lab's `name`), `--home` (default `$ISOTHRUM_HOME`, else `~/.isothrum`), `--json` (events as JSON lines on standard output; text on standard error otherwise), `--param NAME=VALUE`, `--secret-from-env NAME[=VAR]` (values only from the environment, never the command line), `--host-label`, and `--replace` on `up` (remove what exists, then start afresh). `ISOTHRUM_LOG=<level>` shows the runner's tracing on standard error.
- **Run names:** 1 to 63 lowercase letters, digits, `-` or `_`, starting with a letter or digit (Compose's project-name rule); anything else is refused with `run_name`.
- **The runner's home:** `<home>/runs/<run>/` holds `record.json` (the run's record: manifest path and SHA-256, target, driver, state, every non-secret param, start time, last operation), `lock`, `events.jsonl` (the last operations' events, trimmed to its newer half past 4000 lines) and what the manifest keeps in `${run.state_dir}` (Compose's `ports.yml`). Files are 0600 and folders 0700 on Unix. Nothing is written in the lab's folder.
- **What the runner runs in Phase 2:** the `compose` driver only; a `vagrant` or `terraform` manifest, a delivery other than `env`, and the `ready_file` condition are refused as `unsupported` (never reported as ready).
- **Lifecycle rules:** `up` on a running run fails `already_running`; on a parked run it resumes it (`--replace` starts afresh); leftovers of an earlier run are removed first (a `leftovers_removed` warning); a run recorded with another `--host-label` fails `running_elsewhere`. `resume` with nothing left fails `nothing_to_resume` and drops the parked mark. `down`, `park`, `resume` and `check` replay the params the run was started with (they win over the ones given now).
- **Before `up` and `resume`:** each tool of the manifest this host uses runs its probe (25 s), and must answer at its `min_version`; a stopped Docker engine fails here, before anything is created.
- **Limits:** a step runs for its `timeout_s`, else an hour; an action's own Docker calls for two minutes each; a hook for ten minutes. A check runner's limit is the manifest's (no five-minute cap). A run another process operates is waited for a second, then fails `locked`; a lock that can't be taken fails the operation (`io`).
- **Ports:** a fresh run pins each ephemeral host port to a free loopback port, and with `ISOLOOM_PUBLISH_FIXED` set to the port's `preferred` number (once per number and protocol); ports being pinned by another run of the same runner are never handed out twice; every published port is checked free on 127.0.0.1 (and `::1` when something holds it) right before `up`, inside the run's lock.
- **Event stream, version 0:** one JSON object per event with `v`, `seq` (from 1 per operation), `time` (UTC), `run`, `op` and `event` (`state`, `step`, `log`, `ready`, `output`, `check`, `warning`, `result`, `error`); every operation ends with exactly one `result` or `error`. Schema: `crates/isothrum-runner/schema/events-v0.schema.json`.
- **Error codes:** `manifest_invalid`, `manifest_version`, `unsupported`, `io`, `locked`, `tool_missing`, `tool_failed`, `timeout`, `already_running`, `running_elsewhere`, `port_in_use`, `not_parkable`, `nothing_to_resume`, `not_running`, `not_ready`, `secret_missing`, `param_invalid`, `run_name`.
- **Secrets:** a slot's value reaches only the steps its `env` delivery names; every sensitive value is replaced by `***` in events, logs, error messages and the result; a sensitive output's value shows as `***`, and the lab's message never substitutes it. No value is stored.

## Phase 1c: the spec and the run manifest
- **Run manifest schema:** the descriptions name environment variables as code (`` `ISOLOOM_PUBLISH_FIXED` ``, `` `TF_DATA_DIR` ``); the rules are unchanged.
- **Spec problems:** a `dns.servers` name that is no machine suggests the closest machine ("did you mean `dc01`?"); a file with two sources reads "`source` and `input` are both given: keep one source"; the message's placeholder fix is written as code (`` `{{ machines.web.ports.web.published }}` ``).
- **Spec problems, healthcheck:** a `healthcheck` with both `test` and `http` is a `conflict` ("`test` and `http` are both given: a healthcheck is a `test` or an `http` page"); one with neither is an `invalid-value` ("a healthcheck says what to try: `{ test: <command> }` or `{ http: { port, path } }`"), reported when the spec is read (it was a `missing-field` from the checks).
- **Spec problems, `service:`:** a `service:` that is neither a name nor a list says "expected a catalogue service, `name[@version]`, or a list of them".

- **`constraints.proxy`:** an `http://` URL with a one-character host (`http://p:3128`) is accepted; it was refused because its length was compared with `https://`'s.
- **Spec problems found after lowering:** each one's code (`unknown-reference` or `invalid-value`, in `isoloom validate --json`) comes from the check that found it, not from its wording: a `dns.options` value that happens to read `no such` is an `invalid-value`.
- **A machine's `before` is gone from the lowered spec too:** an appliance or an `idle` machine with a process of its own reads "no `command` or `working_dir`" (it named `before` as well).

## Test hosts: the pinned commits
- **`cargo xtask check-all`, SSH hosts:** before a run that copies Isothrum or the launcher, each SSH host (`linux`, `windows`) gets a bare mirror of this machine's Isoloom and Isothrum `main` in its home (`~/isoloom-mirrors/<repo>.git`, fetched from a git bundle each run), its global git config rewrites `https://github.com/isoloom/<repo>` to it (`url.file://<mirror>.insteadOf`, any other rewrite of that URL removed), and its legs run Cargo with `CARGO_NET_GIT_FETCH_WITH_CLI=true`. The host log says which `main` each mirror got. It replaces `~/.isoloom-lab/windows-vm/sync-mirrors.sh` (and its `C:/isoloom-mirrors`).

## The launcher on Windows (launcher repository)
- **Windows, stopping a deploy:** the deploy worker takes Ctrl+C again when it starts, so the Terraform it runs gets a stop's Ctrl+C and stops cleanly (it finishes what it is creating and saves its state). Before, the worker's own process group, which Windows starts with Ctrl+C ignored, passed the ignore on to its tools, and the stop fell back to ending Terraform.
- **Windows, Vagrant on Hyper-V:** the watcher that ends a batch (cancelled, a question Vagrant would wait on forever, the launcher gone, or after 6 hours) runs inside the batch's own PowerShell, starts at once and looks every 500 ms. It used to be a separate PowerShell job, which took 3 s to start on an idle machine and up to 90 s on a loaded one.
- **Launcher lints and ratchet:** the launcher builds, lints and tests clean on Windows and Linux outside `runtime/`. `quality-baseline.json` holds `win32` and `linux` clippy baselines (230 and 244 findings, all in `runtime/`); Windows findings now count in their own area, and `pnpm quality --update` records a platform's first clippy counts. Twelve pedantic lints moved from warn to deny: `cast_possible_wrap`, `cast_sign_loss`, `ignored_unit_patterns`, `large_stack_arrays`, `match_bool`, `missing_panics_doc`, `option_option`, `range_plus_one`, `unreadable_literal`, `unused_async`, `unused_self`, `used_underscore_binding`.
- **`cargo xtask mutants`:** a test run counts as a timeout only after 300 s (`minimum_test_timeout`), since each mutant's run recompiles its doctests; one equivalent mutant of `isoloom-plan` is listed in `.cargo/mutants.toml` (`|` and `^` in `addressing::address`).

## Phase 3: Local VM mode (`vagrant`)
- **`vagrant` target, run manifest:** `generate --target vagrant` also writes `.isoloom/vagrant/run.json` (driver `vagrant`), one file for every provider. `identity.vagrant.providers` lists the eight providers with their hosts, plugin, `elevation` (`hyperv` on Hyper-V), `remote` (ESXi) and Isoloom's refusal for this lab (`null` when it can run there). `identity.vagrant.dotfile` is `${run.state_dir}/vagrant`: the runner runs every Vagrant command of the run with `VAGRANT_DOTFILE_PATH` there, so Vagrant's record of the VMs lives in the run's state, not in `.vagrant/` next to the Vagrantfile.
- **`vagrant` manifest, machines:** each VM by its define name (`native.vagrant`) and its VM name per provider (`native.vm_names`: `<lab> · <machine>` on VirtualBox, VMware, Parallels and UTM; `<lab>-<machine>` on Hyper-V and ESXi; `<lab>_<machine>` on libvirt; none on QEMU). The controller is role `infra` (`keep_running` when the spec keeps it on), the router `infra`, the `shell` tool `tool`. A published port is `fixed` at its `publish` number on 127.0.0.1.
- **`vagrant` manifest, lifecycle:** up is `vagrant.reconcile_provider`, `vagrant.discard_aborted_saved` (VirtualBox), `vagrant up --provider ${run.provider}` (6 h, Ansible's `fatal:` line leads a failure when there is a controller), then the controller halted (`vagrant.park_controller`: `vagrant halt`, and one that fails while the controller powers itself off after its play is waited for until it is off; not on QEMU). Down is `vagrant destroy --force`, `vagrant.remove_orphans` (VirtualBox, Parallels), `vagrant.reset_state`. Park: pause `vagrant suspend <the VMs that run with the lab>` (not a halted controller: Hyper-V refuses to suspend a VM that is off), shutdown `vagrant halt`. Resume: `vagrant up --no-provision --provider ${run.provider} <every VM but a halted controller>`, then, when a saved state couldn't be restored (VirtualBox 7.2 refuses its own VMSVGA saved states: `Failed to load unit 'vga'`), the cut-off state is discarded (VirtualBox) and the same `up` boots the VMs from their disks: the lab comes back without its memory rather than not at all. Provision: `vagrant provision <VMs>` or `vagrant provision ${machine}`, with the controller woken (`vagrant.wake_controller`, as for the checks), its `ansible` play rerun and halted again when the spec has playbooks. Status: `vagrant status --machine-readable` (25 s). Ready: `step_ok up`, then `machines_running` (the lab's VMs).
- **`vagrant` manifest, checks:** one runner per VM with checks, `vagrant provision <vm> --provision-with checks` (the controller's from the networks), each with the docker target's time rule (waits + 15 s per check + 60 s); the controller is woken first (`vagrant.wake_controller`, setup) and halted after (teardown). `ISOLOOM_DERIVED` reaches the runner steps.
- **`vagrant` manifest, slots and params:** each input a VM reads (environment or file) is a slot with `default: ""` and the spec's `sensitive`, delivered to `up`, `provision` and `provision-machine`; each spec secret a VM gets is a required slot from its store, delivered as `ISOLOOM_SECRET_<NAME>`; `ESXI_PASSWORD` is a required connection slot on `vmware_esxi` only. Params: `ISOLOOM_HYPERV_SWITCH` (Windows, Hyper-V, default `Default Switch`), `ISOLOOM_SSH_PROXY_COMMAND` (ESXi, set by the runner), `ESXI_HOSTNAME` (required), `ESXI_HOSTPORT` (22), `ESXI_USERNAME` (root), `ESXI_DATASTORE`, `ESXI_VIRTUAL_NETWORK` (VM Network), `ISOLOOM_DERIVED` (1).
- **`vagrant` manifest, recovery:** a failed start whose output holds `verr_already_exists`, `could not rename`, `is locked`, `different provider` or `single provider at a time` (any case) is cleared (`vagrant destroy --force` within 180 s, orphans, Vagrant's state) and started once more.
- **Vagrant secrets and input files, from the host's environment:** a VM's secret files (a `files:` entry with `secret:` or `input:`) are written by its `secrets` provisioner from the environment `vagrant up` and `vagrant provision` run with (the input's own variable, or `ISOLOOM_SECRET_<NAME>`), then put in place now and at every boot; the set-up no longer waits for a delivery by `isoloom run`. A re-provision given no value keeps the value already kept. Linux and Windows alike.
- **Vagrant inputs on Windows:** a Windows VM's environment inputs (`environment: { X: { input: X } }`) reach its `setup` scripts as well as its PowerShell steps, and are kept as machine-wide environment variables for its `before` and command startup tasks.
- **Vagrant provisioner values travel in base64:** every value a provisioner gets from the host's environment (inputs, secrets) is passed base64-encoded (`isoloom_b64` in the Vagrantfile) and decoded in the guest, since Vagrant writes a provisioner's environment into a double-quoted shell or PowerShell string: a `$(...)` or a backquote in a flag no longer runs in the guest.
- **Vagrant controller on ESXi:** with the default controller box, `vmware_esxi` boots `bento/debian-12` for the controller (Alpine's VMware Tools report no address there, so `vagrant up` waited forever).
- **Vagrant 2.4.0 or later:** the `vagrant` manifest's `vagrant` tool has `min_version: 2.4.0`, the first Vagrant that picks a box's build by architecture (`box_architecture`, the host's by default). An older one takes any architecture's build of a multi-architecture box: Debian 13's packaged Vagrant (2.3.7, says 2.3.8.dev) booted `generic/debian12`'s ppc64le libvirt build on an amd64 host, which hung at the boot loader until `vagrant up` timed out. Install HashiCorp's package (2.4.9 tested on Debian 13 with vagrant-libvirt 0.12.2, the plugin reinstalled with `vagrant plugin install vagrant-libvirt` after the switch).
- **Vagrant on libvirt, box architecture:** a VM booting one of libvirt's own boxes (`generic/*` roboxes builds, the libvirt override of a Debian, Ubuntu, Rocky, Alma or CentOS box, and the controller's Alpine) sets `box_architecture`: the machine's own architecture, `:auto` (the host's) for Isoloom's own VMs.
- **Vagrant on Hyper-V, published ports:** each published TCP port is relayed from this host's `127.0.0.1:<publish>` to the VM's address by Windows' port proxy (`netsh interface portproxy`, the IP Helper service), set at every start (the VM's address on the Default Switch may change) and removed with the VM; the URL the run gives (`http://127.0.0.1:<publish>/`) answers on Hyper-V as on the other providers. A UDP port isn't relayed. It used to be a warning naming the VM's address.
- **Vagrant on Hyper-V, the controller's hostname:** Alpine's controller keeps its box's hostname there: Vagrant sets one on Alpine by restarting every interface, which on the Default Switch closed the SSH session doing it, and `vagrant up` failed.
- **Runner, `vagrant` driver:** a VM lab runs through the runner on the provider the embedder passes (`RunOptions::with_provider`, the CLI's `--provider`); a run keeps the provider it was started on. Before anything is created the provider must be one of the manifest's, exist on this host, not be refused by Isoloom for the lab, and have its Vagrant plugin (`vagrant plugin list`), else `provider_refused` with the reason and, for a plugin, `vagrant plugin install <plugin>`. Every Vagrant command of the run, the driver's own included, runs with `VAGRANT_DOTFILE_PATH` at `<home>/runs/<run>/vagrant`. Status reads `vagrant status --machine-readable` (every provider's state labels: running; poweroff, saved, suspended, paused, shutoff, off, stopped, not_running, powered_off, aborted, aborted-saved are stopped; not_created is absent). A published port reads as its fixed host port.
- **Runner, `vagrant` actions:** `vagrant.park_controller` halts the controller and, when the halt fails while the controller powers itself off after its play (libvirt can no longer reach it over SSH), waits up to 60×2 s for it to be off; `vagrant.reconcile_provider` destroys (within 180 s, best effort) and forgets a run recorded under another provider (a machine counts only with its `id` file); `vagrant.discard_aborted_saved` discards a VirtualBox VM's cut-off saved state (`VMState="aborted-saved"`); `vagrant.remove_orphans` removes this run's VirtualBox VMs (discardstate, poweroff, `unregistervm --delete`) and their leftover folders under VirtualBox's machine folder, or its Parallels VMs, by their exact names from the manifest (never a link's target); `vagrant.reset_state` removes Vagrant's state folder; `vagrant.wake_controller` waits while the controller still powers itself off (`/run/isoloom-halting`, up to 60×2 s), then boots it.
- **Runner, recovery and verdicts:** a failed start is recovered when any line its steps printed holds one of the manifest's `stale_markers`, in any case (VirtualBox's `VERR_ALREADY_EXISTS`). A step's `verdict` leads its error with the matched part of the line (Ansible's `fatal: [host]: …` without Vagrant's machine prefix), cut to 300 bytes.
- **Runner, provider-scoped values:** a param or slot narrowed to some providers or hosts is required and delivered only on those (no ESXi password on a VirtualBox run).
- **Runner, `isothrum provision [--machine <m>]` / `Lab::provision`:** runs the manifest's `provision.all` or `provision.machine` steps (`${machine}` bound) on a running run, with the values given again; `machine_unknown` for a machine the lab doesn't have, `not_running`, `unsupported` without provision steps. Event op `provision`.
- **Runner, Hyper-V elevation:** an operation on a provider with `elevation: hyperv` on Windows runs its tools as they are when the account is elevated or in Hyper-V Administrators; otherwise one elevated session per operation (one UAC prompt, `Start-Process -Verb RunAs`, no `unsafe`): each command a request file in `<home>/runs/<run>/elevated/`, its output and exit code read back, `PATH`, `VAGRANT_*` and `VAGRANT_HOME` forwarded. A declined prompt fails with `elevation_declined`. Status reads are never elevated.
- **Launcher, Settings > Labs > Lab engine:** Built-in or Isothrum runner (saved in the app data folder as `lab-engine`; `CYBERCTF_RUNNER` still forces one). With the runner, container labs on this machine's Docker and VM labs on a local hypervisor (`vagrant`, every local provider) start, stop, park (pause or shut down), resume, re-provision and are checked through the runner; the attack VM still starts beside a VM lab. A VM lab gets checks on its page for the first time.
- **Runner, `tool_too_old`:** a tool answering below the manifest's `min_version` fails the start before anything runs with the error code `tool_too_old` and "`<tool>` is version <found>; this lab needs <required> or later" (it was `tool_failed`). A VM lab needs Vagrant 2.4.0 or later.
- **Runner, a Ruby tool's failure:** a backtrace's frames (`from <file>:<line>:in '<method>'`) don't count among a failed step's last error lines, so Vagrant's own error leads the failure instead of 10 frames.
- **Real runs (2026-10-15), `solo-vm` (one Debian 12 web VM, its flag a file from an input, an HTTP check), through the runner:** Mac, VirtualBox 7.2.20: up (6 min), status, check 1/1, the flag (one holding a `$(…)` and backquotes) intact at 0400 and nothing run in the guest, pause (VirtualBox couldn't restore its own saved state: the VM booted fresh, with a warning) and resume, shutdown and resume, provision, down with nothing left; the same cycle through the launcher's runner path (`real_vm_labs`). friday (Debian 13, libvirt 11.3, vagrant-libvirt 0.12.2, Vagrant 2.4.9): up (6 min), check 1/1, flag intact, pause and resume, shutdown and resume, provision, check, down with no domain or network left. karen (Windows 11, Hyper-V, Vagrant 2.4.9, an elevated account): up, check, pause and resume, shutdown and resume, provision, down with no VM, switch or relay left; the elevated session's broker ran for real (`real_broker` test).
## Phase 3: Server mode (Proxmox through Terraform, ESXi through Vagrant)
- **`proxmox` and `docker-vm` on Proxmox, `node`:** no default any more (it was `pve`); the variable is required and an empty one is refused (`Set node to the Proxmox node the lab's VMs go on`). `pvesh get /nodes` lists a server's nodes.
- **`proxmox` destroy, SDN:** the module has a `proxmox_sdn_applier.finalizer` every SDN object depends on, so a destroy applies the zone and VNet deletions last; none stays pending on the server. The `env` applier runs again whenever the zone or a VNet is replaced (`replace_triggered_by`).
- **`proxmox` router and the `docker-vm` Docker host on Proxmox, the uplink address:** the guest agent's address is awaited 8 minutes (it was the provider's 15; a nested Proxmox under load took four and a half), an IPv4 one (`wait_for_ip`); with none (no DHCP on `uplink_bridge`, or no DNS or internet to install `qemu-guest-agent`) the apply fails with that reason. The VM is stopped, not shut down, on destroy (`stop_on_destroy`), and its address is read with `try`, so a destroy after such a failure still runs.
- **`esxi` router, the uplink address:** with no DHCP on `uplink_port_group`, the apply fails with that reason instead of giving the router's lab address as the lab's address.
- **`proxmox` and `esxi` outputs:** the router's uplink address is `ip` (was `address`); `ready_file` is `/var/lib/isoloom/ready`.
- **`proxmox` machines and controller, the ready file (`isoloom-ready/1`):** each cloud-init step writes `running: <step>` to `/var/lib/isoloom/ready` first (a `run:` step is named by its path, others by what they do: `hosts file`, `waiting for <machine>`, `health check`…); a failing step writes `failed: <step>` and the set-up stops there; `ready` is written at the end. The controller waits for each Linux machine's file to say `ready`, and stops at once on `failed:`.
- **Run manifest, placeholders:** `${run.ssh_public_key}` (the runner key's public half, one line) and `${run.slot}` (the run's slot on its server, 1 to 99: the lowest no other run on the same place holds, kept for the run's life) join the `run.` roots.
- **`proxmox` run manifest (`.isoloom/proxmox/run.json`):** driver `terraform`, the module applied in place with the runner's state (`state: runner`, `-backend-config=path=${run.state_dir}/terraform.tfstate`, `TF_DATA_DIR` in the run's state folder). Up: `terraform.clear_lock`, `init`, `apply`; down: `terraform.clear_lock`, `init`, `destroy -refresh=false` (the state names everything; a router without its agent never holds the destroy); status: `terraform.read_state`; no park. Terraform runs from `hashicorp/terraform:1.9.8` (pinned by digest) on macOS hosts, the host binary (1.6 or later) elsewhere; `ssh` is a tool too.
- **`proxmox` run manifest, values:** the module's variables are params set by the embedder (`node` required; `proxmox_insecure` takes `true` or `false`); `proxmox_password` and `proxmox_api_token` are connection slots; each input a VM reads is an entry of the `inputs` map (`tf_var`, `map_entry`). The runner sets `slot` (`${run.slot}`), `ssh_public_key` (`${run.ssh_public_key}`) and `proxmox_ssh_private_key_file` (`${run.ssh_key}`) itself.
- **`proxmox` run manifest, ready and checks:** ready is the apply, then each Linux VM's ready file (and the controller's), read over SSH through the router (`isoloom@${outputs.ip}`): 40 minutes per machine (2 hours for the controller's playbooks), 10 minutes unreachable at most. Each check runner is `ssh.run` to its machine through the router, `checks/<position>.sh` piped to `ISOLOOM_DERIVED=${params.ISOLOOM_DERIVED} sh -s`. Outputs: `ip`, `ssh_user`, `ready_file`, and each published port at `http(s)://${outputs.ip}:<port>/`.
- **Runner, `terraform` driver (Isothrum):** `isothrum up|down|status|check` run a `terraform` manifest. The state is in the run's folder (`<home>/runs/<name>/terraform.tfstate`), the providers in a shared cache (`TF_PLUGIN_CACHE_DIR=<home>/terraform-plugins`); a `tf_var` delivery is `TF_VAR_<var>`, a `map_entry` slot one key of that variable's JSON object. A failed start's machines read as `failed`, and the next `up` destroys them first. A successful `down` removes the state, its `.terraform`, `known_hosts` and `ssh_config`.
- **Runner, SSH:** the runner's key is `<home>/ssh/id_ed25519`, made with `ssh-keygen` when missing (`isothrum key` prints its public half). A run's SSH reads `<home>/runs/<name>/ssh_config` (the key, the run's `known_hosts`, `accept-new`, batch mode), which `ssh -J` hands to every jump host; `--ssh-jump user@host` (`RunOptions::ssh_jump`) goes first and is recorded at `up`.
- **Runner, ready files:** a `ready_file` condition reads the file's first line every `interval_s`, with the log's last 25 lines; `failed: <step>` fails the start with them, and a host that never answers fails after `unreachable_timeout_s` (default 600 s) instead of passing.
- **Runner, slots:** `${run.slot}` is the lowest of 1 to 99 no other live run on the same place (`--host-label`) holds, kept from the first `up` to the `down`; `slots_full` when none is free.
- **Runner, a tool from its image:** a tool with `container` runs from that image on its `container_hosts` (Terraform on macOS): `docker run` with the lab, the run's folder, the runner's `ssh/` and the plugin cache mounted at their own paths and the environment passed by name; the Docker engine is probed instead of the tool.
- **Runner, macOS relays:** a Vagrant run on `vmware_esxi` from macOS gets loopback relays to the ESXi host's SSH and HTTPS (`ESXI_HOSTNAME=127.0.0.1`, `ESXI_HOSTPORT=<relay>`), `ISOLOOM_SSH_PROXY_COMMAND=/usr/bin/nc %h %p`, a WinRM `http_proxy`, and an `ovftool` wrapper (`<home>/relay/ovftool`) first on `PATH`.
- **Runner, macOS relays, outbound leg:** the relays reach the ESXi host through Apple's `/usr/bin/nc`. A third-party binary started from a terminal (the runner's own, Vagrant's Ruby, Homebrew tools) gets "No route to host" to a LAN or VMware guest under macOS Local Network Privacy; Apple's `/usr/bin/ssh`, `nc` and `curl` are let through. Vagrant's own commands (the plugin check, the reconcile) get the relays' settings too.
- **`vagrant` run manifest, ESXi status:** `lifecycle.status` keeps 25 s on the local providers and gets 60 s plus 30 s a VM on `vmware_esxi` (`provider_timeout_s`): the plugin asks the ESXi host once per VM (41 s for two VMs, measured from macOS through the relay).
- **`vagrant` run manifest, published ports:** each is shown at `http://${host.<machine>}:${value}/`. Locally that is `127.0.0.1` with the forwarded port. ESXi forwards nothing, so on `vmware_esxi` it is the VM's own address (`vagrant ssh-config` `HostName`, what its VMware Tools report) with the VM's own port (`http://172.16.1.146:80/` on `esxi-lab`). A spec message that says `localhost` still says so on ESXi.
- **Run manifest, additive:** `Step.provider_timeout_s` (`{provider: seconds}`, in place of `timeout_s` on those providers only) and the `${host.<machine>}` root (an unknown machine is `unknown_machine`).
- **ESXi through the runner (`esxi-lab`, ESXi 8.0.3, `solo-web`):** `isothrum up --provider vmware_esxi` with `ESXI_HOSTNAME`, `ESXI_HOSTPORT`, `ESXI_USERNAME`, `ESXI_DATASTORE` and `ESXI_VIRTUAL_NETWORK` as params and `ESXI_PASSWORD` as the connection slot: 10 minutes to ready (both boxes uploaded with ovftool through the relay), status 27 to 47 s, the check from the controller passes, park (`shutdown`) and resume keep the address, down in 22 s and the host is left with no VM.
- **Launcher, Server mode through the runner:** with `CYBERCTF_RUNNER=isothrum`, a VM lab on a Proxmox host starts, stops, shows its status and runs its checks through the runner (`.isoloom/proxmox/run.json`): the host's profile as params, its password or API token as the connection slot, the server's first node when the profile names none, and the node as the SSH jump when the lab bridge is internal to it. Container labs on Proxmox (`docker-vm`) and the cloud accounts keep the launcher's own Terraform path.
- **Launcher, ESXi through the runner:** with the runner chosen (Settings > Labs > Lab engine), a VM lab on an ESXi host starts, stops, shows its status, runs its checks and provisions again through the runner (`.isoloom/vagrant/run.json`, provider `vmware_esxi`). The host's address, SSH port, user, datastore and port group are the manifest's `ESXI_*` params. Its password is the run's connection secret, which the runner delivers to every Vagrant command, reads included (`Lab::with_connection`). The run is tied to the server's id, and from macOS the runner relays the host's SSH and HTTPS itself. The lab's address is its VM's own (`http://<vm>:80/`), since ESXi forwards nothing. Pausing stays off for server labs. Container labs on ESXi (`docker-vm`) keep the launcher's own Vagrant path.
- **Runner, macOS relays, a closed connection:** when Vagrant ends an SSH session through the relay, the relay closes nc's input, so the host sees the session end. Before, every session stayed open until the operation ended; ESXi then refused logins (`fork: No space left on device`, about a hundred open sessions) and Vagrant reported "Authentication failed for user root@127.0.0.1".
- **Runner, `vagrant.park_controller` on ESXi:** the controller powers itself off at the end of its play, and ESXi then refuses the guest shutdown `vagrant halt` asks for (`InvalidPowerState`, the VM `poweredOff`). The action takes that refusal as halted and logs one line ("isoloom-controller was already off."), without waiting. The halt's own lines reach the log once it is over, not as they come.

## Phase 1c: Isothrum's tooling, compiler, WASM engine and command line (Isothrum repository)
- **Isothrum's development tasks:** `cargo run -p xtask -- quality [--update] [--table]` (the ratchet, `quality-baseline.json`: clippy's counted lints, files over 400 lines, duplicated blocks, unused and ignored dependencies, `#[expect]` exceptions, per crate), `test` (cargo-nextest, then the doctests), `msrv` (Rust 1.90, cargo-hack; puts back a `Cargo.lock` the older Cargo resolved a dev-link into), `features` (every feature combination), `fuzz [--time SECONDS] [--check] [TARGET...]` and `mutants [--jobs N] [CRATE...]` (the compiler, and the runner's executor; `.cargo/mutants.toml` with capped lints), beside `schema`, `real-run` and `wasm`.
- **Isothrum's lints:** Isoloom's 1c set (`unused` and clippy `all` at deny, the restriction lints, `#[expect]` with a reason, never `#[allow]`); the ones still counted are at warn and held by the ratchet. `deny.toml`: advisories, Apache-2.0-compatible licences, bans, and sources (crates.io and Isoloom's repository). Every crate inherits the workspace's package fields, lints and dependencies, each declared once (a test checks it), and dependencies go one way (the libraries never on a UI or each other; the command line and the desktop app on the libraries).
- **Isothrum's fuzz targets:** `fuzz/` is a workspace of its own; `drawing` (the compiler on any editor JSON) is seeded by the compiler's fixtures. A dev-linked checkout whose `fuzz/` isn't linked is refused (`dev-link link` again).
- **`cargo xtask check-all --repos isothrum`:** Isothrum runs Isoloom's gate list through its own xtask: fmt, typos, machete, deny, clippy on three targets (without `-D warnings`), doc at `-Dwarnings`, quality, msrv, features, fuzz-check and the tests (nextest, then the doctests); `--deep` adds fuzz and mutants. It ran fmt, clippy `-D warnings` and `cargo test` before.
- **Isothrum's Isoloom pins:** `isoloom-spec`, `isoloom-targets` and `isoloom-manifest` (and the desktop app's two) are on one Isoloom commit.
- **Compiler, Windows playbooks:** an Ansible playbook drawn on a Windows node runs from Isoloom's controller (`provision: [{ ansible: <playbook> }]`), the node's scripts staying its own `app.steps`; its starter targets that machine over WinRM (`hosts: <machine>`, `ansible.windows.win_ping`).
- **Compiler, a drawn Linux VM that installs a service** (ports, steps, no command) has no container form under Isoloom's validation: such a lab generates for hybrid (or Vagrant when every machine is a VM), and the desktop app falls back to it from Docker.
- **Compiler API:** `compile` returns the lab's own files with the spec (`Compiled::files`, `into_parts` gives the text, the spec and the files), each path once and never `isoloom.yml` or under `.isoloom/`; `config_files`, `starters`, `vlan_ref`, `config_path` and `firmware_path` are no longer public; `CompileError` is `isothrum_compiler::Error`, and the WASM engine's `EngineError` is `isothrum_wasm::Error`.
- **WASM, one-target download:** a lab file is included when the target's files name it by its path or by its file name (Isoloom's controller runs a playbook from its folder).
- **`isothrum` exit codes and output:** 0 done, 1 failed (a failing check, a refusal, or output that couldn't be written, said once the run is done), 2 a usage error; output whose reader left (`| head`) is no error. An `ISOTHRUM_LOG` value that isn't a level is said as a warning.
- **`cargo xtask check-all`, a host whose clock is off:** when a Linux or Windows host's clock is more than 2 minutes from this machine's, its copies are dated when they land (`tar -m`) instead of keeping their times, so Cargo never takes a changed source for older than its last build there (everything rebuilds), and the host's log says how far off its clock is. karen's was seven hours ahead, and its legs had tested an earlier Isoloom's build.
- **`cargo xtask check-all`, builds dated in a host's future:** before the copies land, a Linux or Windows host's build folder (`<dir>/<key>/target`) is removed when a Cargo stamp in it is dated more than 2 minutes past the host's clock (built while the clock ran ahead), and the host's log says so: everything rebuilds once. After karen's clock was set right, its builds of the day before, dated seven hours ahead, had kept Cargo from rebuilding the changed Isoloom crates.

## Phase 4.1: the configuration model (the step syntax, the resolved recipe, the refusals)
- **Eight step kinds join `app.steps`:** `repository`, `file`, `template`, `user`, `group`, `service`, `command` and `firewall`, beside `run`, `copy`, `packages`, `reboot` and `playbook`. A step is `reboot`, or a map with exactly one kind key; `creates` sits beside `run` or `command`, `unless` beside `command` only.
- **`packages` items:** a name, or `{ name, version }` with the package manager's own version string (`1.30.6-1~bookworm`). `nginx=1.2` is refused (`invalid-value`) with the fix `{ name: nginx, version: "1.2" }`; a decimal version must be quoted. `packages: []` is refused. On Windows a package is a Windows feature (`Web-Server`; it was refused at validation), with no version.
- **`repository`:** `{ name (kebab-case), url (https), key: { url, sha256 }, suite, components, priority }`. `suite` and `components` are apt's (Debian, Ubuntu, Kali): on another family they are `invalid-value`; their defaults are the OS's codename (`bookworm`) and `[main]`.
- **`file`:** `path` and exactly one of `state: directory`, `state: absent`, `link: <target>`, or `url` with `sha256`; `owner`, `group`, `mode`. A `url` without `sha256` is `missing-field` at `<step>.file.url` (fix `sha256: <hex>`); `state: absent` takes no owner, group or mode, a link no mode.
- **`template`:** `{ from, to, owner, group, mode }`, one project file whose `{{ path }}` placeholders Isoloom fills in when it generates: `machine.name`, `machine.addresses.<network>`, `machines.<m>.addresses.<network>`, `machines.<m>.ports.<name>.port`. A run-time value (`.published`, `.url`) or a path naming nothing is reported by `isoloom validate` (with files) at `<step>.template.from`, every placeholder of the file in one problem.
- **`user` and `group`:** `{ name, uid, group, groups, home, shell, system, password }` and `{ name, gid, system }`. On Linux a name is lowercase letters, digits and `_.-` (`invalid-value` otherwise); Windows names may hold capitals (and a group spaces). `password` is a literal (lab content); `{ secret }` or `{ input }` there is `sensitive-value` at `<step>.user.password`.
- **`service`:** a unit name (`nginx`), or `{ name, run, user, cwd, enabled }`: with `run` Isoloom defines the service; `user` and `cwd` without `run` are a `conflict`; `enabled: false` leaves it disabled and stopped.
- **`command`:** a text (`sh -c`; PowerShell on Windows) or a list of arguments, with exactly one of `creates` and `unless`. Without one it is `missing-field` at the step, fix "`creates: <path>` or `unless: <check>` beside `command`, or a `run:` script"; with both, a `conflict`.
- **`firewall`:** `{ allow: [<port name>, <number>, <number>/udp] }`, allow rules only; a name must be one of the machine's ports (`unknown-reference`, listing them).
- **Step paths are typed:** `run`, `playbook`, `copy.from` and `template.from` are project paths (relative, no `..`): an absolute or `..` path is now refused when the spec is read (`invalid-value` at the field), not only by the files check. Paths in the machine are absolute (or a drive path on Windows); URLs are `https`; a SHA-256 is 64 lowercase hex digits.
- **One placeholder grammar:** the message, templates and catalogue entries read `{{ path }}` the same way; a message placeholder outside the grammar now says "isn't a placeholder Isoloom knows", with the paths there.
- **What a VM target runs in 4.1:** `run`, `reboot`, `playbook`, and the first `copy` steps that copy one file with its `mode`, owned by root, before any other kind of step (placed by the VM's `files` step). Any other step is refused at `machines.<m>.app.steps[<i>]`: "a `<kind>` step on a VM is rendered by the configuration renderers, in Phase 4.2" (fix "a `run:` script for now"). This lifts the refusal of those first `copy` steps on VMs.
- **What a container built from steps runs in 4.1:** `run`, `copy` and unpinned `packages`; a `firewall` step needs nothing (a container has no host firewall). A pinned package, a `service` ("runs under Isoloom's runner, which is rendered by the configuration renderers, in Phase 4.2"; fix "`command:` … for now") and the other new kinds are refused at the step.
- **Windows refusals, on every VM target:** a `repository` step (fix `{ run: provision/install.ps1 }`), a file's `owner`, `group` or `mode` (`copy`, `template`, `file`: ACLs come in 1.x), a `file.link`, and a pinned Windows feature.
- **The step-built-server rule is the configuration model's:** a container built from steps with ports and no enabled `service` step or `command` is refused at `machines.<m>.command` ("its steps install services, but no `service` step or `command` runs one in a container"; fix "add `command:` (the service in the foreground); a `service` step runs one in containers from Phase 4.2"). A `service` whose unit has no foreground form (not in the daemon table, no `run`) rules out the container form at `machines.<m>.app.steps[<i>].service`.
- **Daemon warning:** a `packages` step that installs a daemon (nginx, apache2 or httpd, openssh-server, cron or cronie, rsyslog) with no `service` step for it gets a warning at the step ("starts on Debian VMs only"; fix "`service: <unit>`, or `{ service: { name: <unit>, enabled: false } }`"). It is `Lab::warnings()`, never a problem; the `isoloom` command doesn't print warnings yet.
- **`cargo xtask fuzz`:** passes `fuzz/dictionaries/<target>.dict` to libFuzzer when it exists; `spec_syntax`'s holds every field and step kind.

## Phase 4.3: the catalogue engine

- **The catalogue** is `catalogue/<entry>/` in the repository: `entry.yml` (by hand), `lock.yml` (written only by `cargo xtask catalogue refresh`), `contract.yml` (the parity contract) and `files/` (the entry's own templates, each carrying `SPDX-License-Identifier: Apache-2.0`). It is embedded in the binary when built (text files only, under 1 MB); generating never reads the disk or the network for it. `catalogue/daemons.yml` holds the daemons no entry owns (apache, ssh, cron, rsyslog), `catalogue/collections.yml` the pinned Galaxy collections. `catalogue/entry.schema.json` and `contract.schema.json` are generated from the types.
- **An entry is checked when the catalogue loads:** its recipe resolves on every release and OS it lists, with the defaults, each optional setting set in turn and all of them set; every setting is used by the recipe, an image field or a port (and, when the entry has an official image, by something besides `install`); a string that reaches a template keeps to a `pattern` or `values`; a template's `from` is a file of the entry, a `copy` places project content a setting names; the lab's machines are named in a template's file only; the contract has a `default` case and checks of the spec's grammar; each daemon has one owner and a foreground form on every family its unit has; collections are `ansible.*` only.
- **Release matching:** `service: <entry>@<version>` picks the release it equals, else the newest it is a prefix of on dot boundaries (`postgres@16` → the newest 16.x, never 160); no version is the entry's `default`.
- **`with:` is typed against the entry's settings:** `string` (`pattern`, `values`), `integer` (`minimum`, `maximum`), `boolean`, `port`, `endpoint` (`<machine>:<port>`, the machine's address on the first network it shares with this one, or `<address>:<port>`), `folder`, `file`, `password` (a literal, `{ secret }` or `{ input }`; its value file is `/run/isoloom/with/<setting>`, `C:\isoloom\with\<setting>` on Windows, a list item's `…/<setting>/<n>/<field>`; `owner` hands it over at each start) and `list` (`items`, `max`). Problems: `unknown-field` (with a did-you-mean), `missing-field`, `invalid-value`, `unknown-reference` (a secret, input or machine), each at `machines.<m>.with.<key>`.
- **Entry placeholders:** `{{ item.<field>.path }}` joins the grammar (a list item's password file). In an entry, `{{ with.<x> }}` of a folder is its path without the trailing `/`; a secret's or input's value is never written (`{{ with.<x>.path }}` always is, a literal password's too).
- **`cargo xtask catalogue refresh [<entry>…] [--check] [--update] [--propose]`** pins, through `curl`: each repository key (a GPG key's fingerprint checked among the file's primary keys, then its SHA-256; a key the entry pins by SHA-256 checked against it), each official image (Docker Hub only: the tag's multi-platform digest, its `amd64`/`arm64` platforms, its entrypoint and command), each vendor package's exact version per OS (apt `Packages`, rpm `primary`, `APKINDEX`, for x86-64), and the Galaxy collections (version, archive URL and SHA-256). A pin upstream moved fails loudly unless `--update` accepts it; `--check` writes nothing and exits 1 on any drift; `--propose` lists newer upstream releases without adding them.
- **First entry, `nginx`:** releases 1.30.6 (stable, default) and 1.31.7 (mainline) from nginx.org, on debian@12, debian@13, ubuntu@24.04, rocky@9 and alpine@3.24; the official image on debian@13 and alpine@3.24 only; settings `port` (80), `root` (folder), `config` (file), `php_fpm` (endpoint); port `http`.
- **The OS table gains `alpine@3.24`** (`alpine:3.24` pinned by digest; Vagrant box `cloud-image/alpine-3.24`, no Hyper-V build). `alpine` alone stays `alpine@3.19`.
- **The spec's JSON Schema** (`schemas/spec-v1.schema.json`) checks a machine's `with:` against its entry's settings when `service` names the entry; the catalogue writes it.
- **Pinned collections:** `ansible.posix` 2.2.2 and `ansible.windows` 3.8.0 (GPL-3.0-or-later: referenced from Galaxy, never embedded).
- **`service:` resolves through the catalogue** (lowering, design §4.9). The spec no longer refuses a service before the catalogue; the problems are `unknown-reference` at `machines.<m>.service` for an entry the catalogue lacks (fix: did you mean …), `invalid-value` there for a version no release has (fix: its releases), `invalid-value` at `machines.<m>.os` for an OS the release doesn't run on (fix: its OSes), and `with:`'s own (above). A project folder or file a setting names that isn't in the project is `invalid-value` at `machines.<m>.with.<setting>` (`isoloom validate` with files).
- **A service machine's ports are its entry's:** `ports.<name>` may only `publish` (or mark `dormant`) one of the entry's ports; `ports.<name>.port` on a service machine is `conflict` ("a catalogue service's entry gives its ports' numbers"), a name the entry lacks `unknown-reference` (fix: its ports). Its health is the entry's unless `healthcheck` gives one; its data are volumes at the entry's paths (a volume of the same name or path is `conflict`); its passwords are value files (mode 0400, root's).
- **A service machine's forms:** on a container target, the entry's official image (pinned by digest) where the release publishes one for the machine's OS and architecture, with a thin build of `configure` and its own entrypoint and command; else built from the OS's image with the whole recipe. On a VM target, a fresh VM of its OS set up by the recipe. Refused at `machines.<m>.service`: several services on a container target ("several services share a VM, but a container runs one"), a `start` that reboots, a daemon with no foreground form; at `machines.<m>.hardware.arch`: an image that doesn't publish the machine's architecture ("<entry> <version> publishes no `arm64` image"; fix: another release, or `amd64`).
- **Until the configuration renderers carry every step (Phase 4.2),** a service machine whose recipe has a step the target's form can't render yet is refused at `machines.<m>.service`: "<entry>'s recipe: a `<kind>` step in a container is rendered by the configuration renderers, in Phase 4.2" (or "on a VM"). Over the official image a container runs the entry's `configure` alone (the image is `install`, and its own entrypoint prepares each start from `image.environment`, which becomes the machine's environment on container targets, the machine's own variables winning), plus a `copy` of each project path `image.files` names; an entry whose image runs its `start` steps through Isoloom's runner (`image.start: run`) is refused there for now ("no container renders it yet"; fix: a VM target).
- **`resolved.json`** lists each service machine's `services`: `entry`, `release` (the one its version picked), `source` (`vendor`, `distro`, `download`) and `image` (the official image with its digest, or null when the container is built).
- **`cargo xtask catalogue check <entry> [--release V] [--os OS] [--form container|vm|both] [--case C…] [--runner PATH] [--provider P] [--keep]`** runs an entry's parity contract for real: each case becomes a lab (the service machine `web` with the case's `with:` and project files, its helper machines on the same OS, and an access machine `probe` the runner supplies, on one network with the internet), generated by the checkout's `isoloom` for `docker` and for `vagrant`, then run through the Isothrum CLI (`up --replace`, `check --json`, `down`; its own run name and home under `target/catalogue-check/<entry>/`). A check runs from `probe` (an `exec` in `web`); each fact is run as a check of its own, `fact: <name>`, whose reported output is its value. A case passes when every check passes in both forms and every fact reads the same in both; a case whose helper names an entry the catalogue doesn't have yet is skipped. Exit 1 when a case fails. Defaults: the entry's default release on its first OS, both forms, `isothrum` on `PATH`, `virtualbox` (`libvirt` on Linux).

## Phase 4.2: the floor renderers (shell and PowerShell libraries, the Dockerfile, the runner)
- **Every step kind renders on every form:** a VM (Vagrant, Proxmox, ESXi, the clouds) runs `repository`, `packages` (with versions), `copy`, `template`, `file`, `user`, `group`, `service`, `command` and `firewall` in its set-up, in step order, between its scripts, playbooks and reboots; a container built from steps runs them in its image's build. The refusals "… is rendered by the configuration renderers, in Phase 4.2" are gone, on VMs and in containers, for apps and for catalogue entries.
- **Existing hosts (`external`)** still run only `run`, `reboot` and `playbook`: any other step is refused at `machines.<m>.app.steps[<i>]` ("a `<kind>` step on a host that already exists runs with the Ansible CM tool (Phase 4.5)"; fix "a `run:` script for now, or a VM target"), and an entry's at `machines.<m>.service`.
- **The shell library** (`.isoloom/configure/lib/configure.sh`, POSIX `sh`, Apache-2.0): one function per step kind for apt, dnf (yum on CentOS 7) and apk, systemd and OpenRC, each behind its guard, so applying a recipe twice changes nothing; every change prints `isoloom: changed <what>`. A Linux VM's set-up step embeds it (without its comments) before the step's calls; a generated Dockerfile `COPY`s it to `/usr/local/lib/isoloom/configure.sh` and `RUN`s one call per step. The file is generated when a recipe calls it.
- **The PowerShell library** (`.isoloom/configure/lib/configure.ps1`): the same for Windows VMs (`Install-IsoloomFeature`, `Copy-IsoloomItem`, `Install-IsoloomTemplate`, `Install-IsoloomFile`, `Add-IsoloomUser`, `Add-IsoloomGroup`, `Register-IsoloomService`, `Register-IsoloomTask`, `Invoke-IsoloomCommand`, `Enable-IsoloomFirewallPort`).
- **Restart rule:** a `service` step restarts its service when an earlier step of the same apply changed something; a service after a script, playbook or reboot always restarts (the rule errs on restarting).
- **`template`:** the project file is read by `isoloom generate` and filled in (`{{ machine.name }}`, `{{ machine.addresses.<net> }}`, `{{ machines.<m>.addresses.<net> }}`, `{{ machines.<m>.ports.<name>.port }}`) for each machine on each target; a VM's set-up carries it base64-encoded, a container's build `COPY`s `.isoloom/configure/<m>/rendered/<from>`. Mode `0644` when none is given. A template that couldn't be read fails the step ("the template <from> wasn't read when the files were generated").
- **`user.password`:** hashed with SHA-512 crypt (`$6$`), its salt derived from the lab, the machine and the user, so the generated files are the same at each generation; Windows gets it plain (it takes no hash). An existing user's supplementary groups are added to, never removed.
- **A service Isoloom defines (`service: { name, run, user, cwd }`)** is a systemd unit (`/etc/systemd/system/<name>.service`, `Restart=on-failure`), an OpenRC script on Alpine, or a startup task (`isoloom-<name>`, as SYSTEM) on Windows; `user` on Windows is refused ("a Windows service Isoloom defines runs as SYSTEM in 1.0"), as are a Windows account's `uid`, `home`, `shell` and `system` and a Windows group's `gid` and `system`.
- **`command`:** a text runs through `sh -c` (PowerShell on Windows), a list as it is; `unless` with a list runs it as it is.
- **`run` with `creates`** is now skipped on VMs too when the path exists (it was only in containers).
- **`firewall`:** opens each port with `firewall-cmd --permanent` when firewalld runs, `ufw allow` when ufw is active, nothing otherwise; Windows Firewall rules are named `isoloom-<port>-<TCP|UDP>`. A container needs nothing.
- **Isoloom's runner** (`.isoloom/configure/<m>/run`, installed as `/usr/local/bin/isoloom-run`, the image's `ENTRYPOINT`): a container whose steps start one service runs it in the foreground (`exec`, dropping to its `user` with `setpriv`, or BusyBox `su`), its log files linked to the container's output (nginx's access log to stdout, its error log to stderr); several services (or one and the machine's `command`, passed as the runner's arguments) start in step order, each output line prefixed `<unit> | `, and when one exits the runner stops the others and exits with its status, so the engine restarts the container. A container with services is no longer kept idle (`sleep infinity`).
- **Compose `init: true`:** on a container whose process is Isoloom's runner, a container kept idle, an idle tool, the check stand-in, and Isoloom's own infrastructure containers (`isoloom-router`, each `<machine>-routes` sidecar, the VLAN switches). They now stop on `SIGTERM` at once (exit 143) instead of being killed after Compose's 10-second timeout (exit 137): a real `isothrum park` of `segmented` took 3.2 s, `down` 6.9 s.
- **Kubernetes `shareProcessNamespace: true`** on a pod whose container runs Isoloom's runner (the pause process reaps orphans).
- **Examples `configured-app` and `configured-windows`:** an app written in the configuration model (nginx with a template, a user, a group, files, a guarded command, a firewall port, and two services Isoloom defines on Ubuntu), and a Windows server (IIS as a feature, a template, a local user and group, W3SVC); both ship their files and pass `isoloom validate`.
- **`cargo xtask conformance [--family debian-12|ubuntu-24.04|rocky-9|alpine-3.24]… [--renderer shell|dockerfile]…`:** the configuration renderers' resource conformance. A recipe with every step kind a container can hold (nginx.org's repository, a package, a group, a user with a password, a folder, a link, a pinned download, a removal, a file and a folder copied, a template, two guarded commands, a firewall port) is applied by each renderer in each family's pinned official image (the VM's set-up script in a fresh container; the container form's image, then the VM's script in it); a probe checks each kind's state, and the second apply must print no `isoloom: changed` line. A table per family × renderer is printed and written to `target/conformance/report.txt`; exit 1 when a kind fails. `cargo xtask check-all --deep` runs it (it needs Docker and the network).
- **`cargo xtask fuzz`'s `quoting` target** also reads back a systemd unit's word (`ExecStart=` of a service Isoloom defines) and a template's text base64-encoded in a shell word.
- **An official image whose entry runs its `start` steps through Isoloom's runner (`image.start: run`)** is no longer refused on container targets: the thin build over the image installs the runner as its `ENTRYPOINT`, its `CMD` the image's own command (or the entry's `image.command`); at each start the runner runs the `start` steps (scripts copied into the image, the others through the shell library), then `exec`s the image's own entrypoint with that command. ## Phase 4.4: the cloud-init renderer for the configuration model
- **cloud-init now carries a machine's configure steps compressed.** On a target that hands a VM its user data (Proxmox snippets), each `Step::Configure` is delivered as a `write_files` entry at `/var/lib/isoloom/configure/configure-<n>.sh` with `encoding: gz+b64` (the shell library and the recipe's calls, gzip then base64), run from `runcmd` with `sh <path>`. - **User-data size limits.** `isoloom_render::configure::cloud_init::Limit` names each cloud's cap (AWS 16 KiB, Azure 64 KiB, Google Cloud 256 KiB) and `Limit::fits` refuses a document over it, naming the provider and the overflow; gzip keeps a recipe's script small. - **`verify` checks the embedded configure script.** The cloud-init shellcheck now decodes a `write_files` entry's gzipped content (`gz+b64`, `gzip`: the configuration carrier's script) before checking it, so a recipe's compressed script is shellchecked, not skipped. - **The verify image resolves the pinned Ansible collections.** `tools/verify/Dockerfile` installs `ansible.posix` and `ansible.windows` at the versions `catalogue/collections.yml` pins (SHA-256 checked), where `ansible-lint` finds them (`ANSIBLE_COLLECTIONS_PATH`), so the generated `site.yml` and roles are linted with their modules resolved. The collections are GPL-3.0: referenced by the validator and the generated `requirements.yml`, never embedded in Isoloom or its output.
- **The generated `requirements.yml` carries each collection's pinned sha256** (security finding C2). It records `name`, `version`, `source` and the `sha256` that `catalogue/collections.yml` pins, so a run checks the archive against the pin before installing and can't fetch a mutated collection; the checksum was dropped before. `ansible-galaxy` ignores the extra field, so `ansible-galaxy install -r requirements.yml` still works.
## Phase 6: hardening — security-review fixes
- **A VM file's `mode` is single-quoted in the generated `chmod`** (security finding S2). The `machines.*.files[].mode` value now reaches the set-up script as a quoted shell word (`chmod '0644' /path`), so even an unvalidated mode can't break out of the command. Validation still restricts it to octal digits; this is defence in depth for library consumers that render a lowered spec without validating it.
- **A privileged container on an `internet: false` network is now refused** (security finding S1). `isoloom validate` rejects a container (`docker`/`app`, not a `vm`) with `privileged: true` attached to any network whose `internet` is false, because the offline seal is enforced inside the container's own network namespace (a removed default route) and a privileged container could add the route back. The message names the machine and the network; the fix is to drop `privileged` or move the machine to a network with internet. VMs are unaffected (they are sealed at the hypervisor or router, out of their own reach).
